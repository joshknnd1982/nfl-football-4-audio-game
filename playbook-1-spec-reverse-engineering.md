# Playbook 1: Specification and Reverse Engineering

Reference file of the Kitchen and PCS Games Revival Playbook. The always-loaded rules are in `CLAUDE.md` (section 0 rules including 0.8 automation first, evidence tags, working style, phases, folder layout and legal notes all still apply). Read for phases P1-P5; P4 and P5 also read 7.8 and 7.9 in `playbook-2-clone.md`. Section numbers are global across the playbook.

---

## 5. Specification

### 5.1 GAME_SPEC.md template
Enough for a developer who never saw or heard the game to build an exact game. Sections: 1 overview; 2 source facts (files, sizes, SHA-256, toolchain, p-code/native, packer, runtime, DirectX version); 3 program flow (startup, main loop/events, shutdown, each screen/state); 4 menus (items, exact text, key, result, sound/speech); 5 mechanics (rules, formulas, constants, tables, limits, order of operations); 6 randomness and seeding (5.5); 7 timing (ms); 8 input (every key per state, invalid input, repeat/buffering); 9 text and speech (exact wording, when, variables; STRINGS.md; which screen reader or speech API the original calls, if any, 6.2); 10 sound (every wav: properties, trigger, loop, overlap, volume/panning; WAV_EVENT_MAP.md; gaps and additions, SOUND_DESIGN.md); 11 maps, levels, teams, rosters, data, with every customizable list and original limits (count, length, characters; 7.9); 12 files (each read or written: field-by-field format, how the original handles missing/corrupt files); 13 accessories and helpers (readmes, help, config, helper EXEs, DLLs); 14 loops, conditions, syntax notes with procedure index pointers; 15 error handling, edge cases; 16 child games and links; 17 game notes (decisions, modernizations, additions, what must stay exact; the additions every game has: the 0.16 welcome in the place of the original's spoken title and the 0.15 debug log, which writes only into its own logs folder and never touches a log file the original itself kept); 18 checklist results; 19 open questions (pointer to `spec/OPEN_QUESTIONS.md`, with the answered ones summarized).
A spec written in discovery order is put into this order in S5.1 by script, never by hand: copy the draft, move the sections, edit only by adding words, and prove with a checker that every word of every old line, every evidence tag and every quirk's decision survived (nfl4 is the model: `work\reorder_spec_s51.py`, `work\check_spec_s51.py`, GAME_SPEC 16 to 19; fixesforgames A37, B-T26).

### 5.2 STRINGS.md and WAV_EVENT_MAP.md
STRINGS.md entry: ID, exact text, encoding and offset/source, event/menu/choice, variables, evidence tag. Record the original's caption, spoken title and first-run welcome (with the words spoken before and after them) as ORIGINAL entries and, next to them, the game's window title (0.5.1) and welcome sentence (0.16, 7.12) as CLONE entries, so the replaced words and the order of the original's opening events are known when the game is built.
WAV_EVENT_MAP.md entry: sound ID (stable, e.g. `menu_select`), kind (ORIGINAL-WAV; ORIGINAL-TONE = PC speaker; GENERATED = addition of this game; USER = player replacement), file, size, format (rate, bits, channels, duration), event, code location, loop/one-shot, confidence. Non-wav sounds (beeps, tones, music strings): frequency or notes, duration, code location. Also list every event that plays a sound and every file no code references (mark unreferenced, never discard). Numbered names (foot0, foot1, foot2 ...) are grouped into families only where the code draws among them for one event (a pool); a pool is ONE family entry with its first number, members, draw rule and the source of its upper limit, and numbers that are different sounds for different events stay separate (7.7.1, CLAUDE.md 0.14).
Unknown wav-to-event: first settle it yourself: code references, file names, nearby strings, resource names, duration, loudness envelope, simple spectral features (pitch, noisiness), how similar sounds in the same game are named; tag GUESS only if that fails. Claude cannot hear. Collect every wav still uncertain and settle them together in listening rounds with the keyboard-only review tool `tools/sound_review` (built once, the first time it is needed, reused in 7.8; it exists since nfl4 P4 S4.1: `games\tools\sound_review`, README there; a round file per round in `observations\`, started with `sound_review.cmd <round file>`, answers in `<round file>_answers.txt`; fixesforgames B-A9, A34): it speaks each file's name, plays it, and lets the owner mark what it is; 5-10 wavs per round, no one-at-a-time chat questions. Marked wavs become OWNER-CONFIRMED. Until a round happens the item stays owner-needed in `OPEN_QUESTIONS.md` and the game uses the GUESS.

### 5.3 Evidence tags
CODE (recovered code, disassembly, resources); OBSERVED (watched or captured the original running); OWNER-CONFIRMED; INFERRED (give reasoning); GUESS; UNKNOWN (also in `OPEN_QUESTIONS.md`). Before freeze try to upgrade every GUESS and UNKNOWN (code, captured runs, web search, tests). For those that remain, record a recommended default and the phase whose test will confirm or break it; list them once for the owner, who may accept all or change any. Items that need ears or play go to the listening rounds (5.2) or the P8 playtest.

### 5.4 Completeness checklist (P5 audit)
Each item answered, not applicable (with reason), or recorded as unknown with a default decision and the phase that will test it: all strings tied to events, menus, choices; all wavs tied to events, plus unreferenced files; all PC speaker tones, beeps, music strings tied to events; every silent event and its decision (silent or generated sound); all menus and choices with exact keys; all loops, conditions, functions, procedures marked done; all mechanics, formulas, constants, tables, random behavior; all maps, levels, rosters, tables; every customizable list with original limits (7.9); all files, data files, formats; all text files and everything else in the folder; all accessories and helpers; all events and their order; timing; error and bad-input behavior; what the original does when its own file is missing, empty, or corrupt (recreate, defaults, or fail; exact files and contents); startup and shutdown incl. what is spoken or played (and where the 0.16 welcome takes the place of the original's title or welcome, 7.12); every log or text file the original itself writes while it runs (these are original behavior and stay as the original makes them; the game's own debug log, 7.11, is separate and additional); child games. The gap items of this list (timing, speech and key mechanics, flow at the end of a game or season, files, errors, bad input, randomness, added texts) are answered in S4.3 in `spec/GAP_REGISTER.md` (nfl4 is the model, fixesforgames A35): one entry per gap with status SETTLED, DEFAULT or NOTED, the evidence tag, what the original does, what the game does, and the session that closes each default; counts are written by a script, never by hand. The silent events and the system sounds are answered in S4.4 in `spec/SOUND_DESIGN.md` and every customizable list in S4.5 in `spec/CUSTOMIZABLE_CONTENT.md` (nfl4 is the model for both, fixesforgames A36). The auditor is a fresh reviewer (another session or a subagent that has not seen the work being produced), not the author. The author verifies every finding in the code before acting, fixes by adding words and proves it with the checker against the audited copy (nfl4 S5.2 is the model: 34 findings, all real, 3 of them would have changed play although every script passed; fixesforgames A38).

### 5.5 Faithful random numbers
Check how the game calls and seeds random numbers (Randomize, Randomize Timer, a value, none). Verify against the disassembly, do not assume: VB6 Rnd is next = (previous * 1140671485 + 12820163) mod 2^24, result next / 2^24, initial seed 0x50000; QuickBASIC 4.5 similar, multiplier reportedly 16598013. Clock-seeded: match range and distribution, note it.

## 6. Reverse engineering

6.1 Principles. Static first, dynamic second, captured observation third, owner observation last. Claude cannot hear audio or play an audio game: analyze wavs by file properties (duration, silence, waveform shape, spectral features) and ask the owner only for what needs ears. Claude Code runs on the owner's PC: run tools, scripts, debuggers, tests yourself. Launch the original only when its behavior can be captured: DOSBox-X with scripted keystrokes, logs, memory dumps and screen-text dumps; debugger traces; output files; for Windows programs, UI Automation or screen-text capture of labels and text boxes, and the screen reader's speech log if one is running (verify what the installed NVDA offers, or the JAWS speech history if the owner has JAWS); else use 6.4. Run unfamiliar old executables only where they cannot harm the PC: Windows Sandbox (availability checked in S0.1), a VM, or DOSBox-X for DOS programs; static analysis needs no running at all. Set up that safe environment yourself; ask only if enabling it needs administrator rights or a reboot. Prefer free tools (Ghidra, DOSBox-X debugger, x64dbg, Reko, ndisasm); a paid tool is never bought or installed without the owner's yes, so use it only if free ones cannot do the job.

6.2 VB6 (Jim Kitchen). Identify: imports MSVBVM60.DLL, VB5! header, ThunRTMain (Detect It Easy or a PE viewer); p-code = tiny native stubs calling the runtime with logic as byte code; native = real x86 with many `__vba...` calls. Extract: strings are UTF-16 (get UTF-16 and ASCII; catch strings built at runtime, e.g. prefix + number + ".wav", and record how); forms, controls, control arrays, menus, timers with intervals, text boxes, labels, KeyPress/KeyDown/KeyUp; Declare statements, DirectX libraries (dx7vb.dll or dx8vb.dll), other DLL/OCX dependencies, and any screen reader or speech API it calls (jfwapi.dll or FSAPI, FreedomSci.JawsApi, nvdaControllerClient, Window-Eyes, SAPI; record it in the spec); files opened (Input, Output, Append, Random, Binary, Get/Put user types, INI via Private Profile, registry via SaveSetting/GetSetting) and what happens when a file is missing, empty, or damaged (many recreate files with original values: record files, contents, when). Decompile: p-code with a decompiler such as VB Decompiler (verify capabilities and license; it is commercial with a limited trial, so check first whether free tools or the trial are enough); native with Ghidra plus `__vba` names; x64dbg (32-bit mode) to confirm runtime values; decompiler output is a starting point, verify important logic. Find how text reaches the player (label, text box, list box, caption, screen reader), which control changes and when; the game speaks the same text at the same moments.

6.3 MS-DOS (PCS and similar, incl. QuickBASIC EXEs). Identify first: MZ or COM; packers (LZEXE, PKLITE, DIET, UPX) unpacked first; QuickBASIC runtime text (errors like "Illegal function call", "Subscript out of range", a run-time library copyright string) and any external runtime module (BRUN45.EXE etc.) kept in the game folder; signs of Turbo Pascal, Borland C, PowerBASIC, assembly. Extract: ASCII strings with offsets and file order; how wavs reach the speaker (Sound Blaster ports 0x220/0x240, BLASTER variable, external wav players, SHELL, helper EXE/DRV/COM; game reproduces the result, not the method); PC speaker sound (SOUND, BEEP, PLAY, direct timer/speaker ports): each frequency and duration (QuickBASIC SOUND durations are clock ticks, ~18.2/s; verify), every PLAY string exactly, its event; these are ORIGINAL-TONE, reproduced exactly (7.8); how text reaches a blind player (DOS screen reader, hardware synthesizer, video memory, plain output); file operations, runtime-built file names, data formats, behavior when a file is missing or damaged. Analyze with a 16-bit disassembler (Ghidra, Reko, ndisasm) and the DOSBox-X debugger; capture DOSBox-X screen text and compare with strings. No reliable QuickBASIC decompiler: rebuild logic from disassembly, runtime behavior, transcripts; say what is inferred.

6.4 Owner observation, last resort: only for what 6.1 capture, code, and analysis could not settle. Collect the needs, then ask: one small request at a time, exact keys, what to listen for or read; ask what was spoken, what sound played, in what order; save in `observations/` with date, steps, result, tagged OBSERVED or OWNER-CONFIRMED. Do the capture work yourself where possible (screen reader history or log to a text file, scripted keystrokes), so the owner only listens.

6.5 Menu programs: reverse-engineer the menu itself, list launched games as child games, each with its own folder and project.
