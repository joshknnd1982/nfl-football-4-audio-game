### 7.11 The detailed debug log (owner rule 2026-10-18, CLAUDE.md 0.15)
Owner: "all games must have a detailed debug log so that Claude can easily debug games that I make, especially since everyone's computer setup is different from mine." Claude cannot see, hear or touch another player's PC, and a blind player at the keyboard cannot describe a Windows setup or read a traceback, so the log is Claude's eyes and ears: one file that says what the PC is, what the program did and what went wrong. Every game has it from S7.1. Status on 2026-10-18: nfl4 built the detailed log in SX.L (`data/debuglog.py` the core, `data/sysreport.py` the startup report, `data/problem_report.py` the zip, `data/logsetup.py` the entry points, `game/tools/read_debug_log.py`, `tests/test_debuglog.py`, `tests/test_read_debug_log.py`; fixesforgames B-R9 to B-W12 hold the lessons of its independent review); the starter kit still holds only the plain rotating log and takes the nfl4 files when it is refreshed (fixesforgames section C). The list is the contract; the names of files and functions are the kit's.
- Where and how long. The per-user logs folder (`paths.log_dir()`, never the program folder: 7.2.1, 9.1.1). One file per launch, `<slug>-YYYYMMDD-HHMMSS.log`, plain UTF-8 text, one event per line; the newest 10 launches are kept and older ones deleted at the next start. A launch is capped at 10 MB as a ring of two halves (when one half is full the other starts and the older half is dropped; the startup report is written again at the top of each half), so a long session never fills the disk and the report is never lost. A second file `<slug>-crash.log` (1 MB cap, kept across launches) receives `faulthandler` output: `faulthandler.enable(file)` for native crashes (a voice DLL, 7.4.5) and a watchdog thread that dumps every thread's stack once when the game thread has shown no heartbeat for 10 s (a hang). A windowed exe has no stderr: always open the files by handle.
- Level. A setting `debug_log` in `settings.txt`, also an item of the speech settings menu: `detailed` (default; DEBUG), `trace` (adds every random draw and every internal queue step; asked for from a player only after a first report needs it), `normal` (INFO and above) or `off`. `off` is the player's right; the README says a bug cannot be fixed without a log. `--debug-log=trace` and the variable `<SLUG>_DEBUG_LOG=trace` set it for one launch.
- Format. `HH:MM:SS.mmm +elapsed LEVEL thread component event key=value ...`, one event per line, every value on the same line (a newline in a value is written as `\n`), one run id on every line, so `grep` and the reader tool find things. No paragraphs of prose.
- The startup report is the first block of every file (about 60 lines of `key = value`), each item with a value or `n/a (reason)`, never silently missing. Program: game, version, build date, source commit if known, 32 or 64 bit, frozen exe or source, installed or portable, the exe path, the program, data and log folders, the working directory before and after `leave_program_folder` (7.2.1), the welcome sentence spoken (7.12). Windows: version, build, edition, 32 or 64 bit, display language, locale, code page, time zone, administrator or not, DPI, CPU count, memory, free space of the data drive, and whether the data folder, Documents and Desktop are redirected by OneDrive or sit on a network or removable drive. Software: Python and package versions; the process names of the screen readers and speech tools running (NVDA, JAWS, Narrator, others by name only). Speech, per backend: NVDA (controller DLL path, its version, load result, `testIfRunning` result, NVDA's own version), JAWS (installed, running, COM result, version), SAPI5 (every engine and voice with token, language, the bitness of its engine DLL and the registry hive it came from; the voice chosen and why; the output mode setting and what `automatic` turned into; the time of the first test utterance). Audio: library versions, the output devices found and the one opened, rate, channels, buffer, result, how many sounds loaded, which are missing or damaged. Files: the settings as read; every customization file with its health (ok, created, reset, damaged, locked, unwritable, 7.10). Environment: a whitelist (`LOCALAPPDATA`, `APPDATA`, `TEMP`, `PROCESSOR_ARCHITECTURE`, `OneDrive`), never the whole environment.
- During play, at DEBUG, with times in ms. Every key (name, modifiers, repeat) with the screen and menu item it reached and what it did. Every menu step. Every speech request (text, interrupt, voice or role), the backend that took it, the time to accept and to end (7.4.4), the queue length, every failure with its code or exception and every fallback to another backend. Every sound played (ID, the file chosen and which link of the 7.7 chain chose it: player file, pool member, original, generated or silence; slot, volume, pan, pitch, loop, result) and every underrun. Every file read, written, created, healed or copied aside (path, size, result, damage kind, 7.10). Every setting changed (old and new). The events the game logic reports, those a golden transcript holds (B-X22), and the random seed of every game, season or franchise at its start, so a session can be replayed. Startup phases in ms; any step slower than 200 ms as `SLOW name ms`; a heartbeat every 30 s with the state of the game thread; the reason for leaving (menu, window close, error, exit deadline) and a last line `closed` (`exe_smoke.py` waits for it, 7.2.1). `trace` adds every random draw (n, result) and every queue step.
- Errors. No `except: pass` and no swallowed exception anywhere. A caught error is logged with its traceback where it is caught (an expected one at DEBUG with the reason, an unexpected one at ERROR); the last-resort handler and `install_exception_logging` cover every thread (7.10); a fallback (voice, backend, sound, file) is a WARNING that names what failed and what was used instead.
- Privacy, in one place. Before a line is written, one `redact()` inside the log formatter (so no call site can skip it) replaces the Windows account name in every path with `<user>`; the log never holds the computer name, an e-mail address, a password, a key or a token; text the player types is written as its length and whether it was accepted. The saved game and the player's own text files are never copied into a log. The program sends nothing anywhere (no upload, no telemetry): the player sends the file.
- Never in the way. Lines go through a queue to a daemon writer thread (a call costs well under 1 ms; the key-to-sound tools of 7.4.3 are run with `trace` on and must show no change); `finish()` flushes the queue before `os._exit` (7.2.1); a formatter or disk error is swallowed, counted and reported in the next launch's startup report (`log_errors_last_launch`). An unwritable, locked or full logs folder falls back to the temp folder, then to no file; the game starts, speaks and plays as always and the player hears nothing about it. One hour at `detailed` should stay near 5 MB.
- Getting it to Claude. The players use the keyboard only and cannot be asked to find a path, so a menu item (the speech settings or help menu, its key in the help text) "Save a problem report" makes `<slug>-problem-report-YYYYMMDD-HHMMSS.zip` on the Desktop (else Documents), speaks the full path and offers to open the folder. The zip holds the newest 3 launch logs, the crash log, `settings.txt`, the list of customization files with their health, `system.txt` (the startup report made again now) and `README.txt` (what it is, where to send it); saved games go in only if the player says yes to one question. The same from the command line: `<exe> --problem-report` (no window). Every game's README has "If something goes wrong" (the keys, the logs folder, where to send the zip: the repository's issues or the owner's e-mail) and the repository has `.github/ISSUE_TEMPLATE/bug_report.md` (what happened, what you pressed, Windows, screen reader and its version, the zip attached). Uninstall keeps the logs with the other per-user data and removes them only with the delete switch (0.10, 8.2).
- How Claude reads it. `game/tools/read_debug_log.py <log or zip>` prints, in this order: the setup in ten lines; every WARNING, ERROR, SLOW and failure with a count per backend; the 40 lines before the first ERROR and before the end; the settings and customization health; the seed. `--replay` builds the key script for the test rig from the seed and the keys and runs the session on the game (games with a golden-transcript rig, B-X22). A failure that comes from the player's setup is reproduced with the fake speech and sound backends set to fail the same way (the voice list, the code, the delay from the log), never by guessing. Claude asks for the zip before it asks the player a question the log can answer. Every fix of a reported bug adds the log line that would have shown it, and its entry in `fixesforgames.md` names that line.
- Tests (`tests/test_debuglog.py`, the exe smoke test, S8.3): a start writes every key of the startup report with a value or `n/a (reason)`; a failing fake voice, a missing sound, a damaged settings file, an exception in a worker thread and a write to a read-only file each leave their line at the right level; the Windows account name of the test user (and a name with accents and spaces) appears in no file; an unwritable folder, a full disk (a tiny quota) and a file locked by another program each leave a game that starts and plays; 30 MB of lines keep the files under their caps, with the report at the top of each half and only the newest 10 launches; `finish()` leaves `closed` as the last line; the built exe on an empty data folder writes the report and the last line (`exe_smoke.py`); `--problem-report` and the menu item make a zip with exactly the listed members and `<user>` also in the settings copy; the median key-to-sound difference with `trace` on is under 1 ms; a recorded seeded session replays from its own log to the same speech and sound events. S8.3 adds: the problem report made from three launches at their cap with the account name in every line (in time, nothing leaks); a destination that fills up in the middle leaves no half-written zip (the zip is written under a `.part` name and renamed when whole, fixesforgames B-R11); logs that are folders, binary junk or UTF-16; a report made while the program writes its log; the program started with a file where its logs folder belongs, with a full disk for the log, and with an old log held open by another program.
- Other platforms (9.1): the same list in the platform's place (Linux `~/.local/state/<slug>/logs`, macOS `~/Library/Logs/<game>`, Android and iPhone the app's private folder with a share action for the report, on Android also logcat lines with the same events), with the startup report's probes behind the small interfaces of 9.3.

### 7.16 The T key calls a timeout, anywhere in a football game (owner rule 2026-10-20, CLAUDE.md 0.22)
The owner, while nfl4's plays were being researched: a timeout can be called as long as the play has not been run, as in real NFL and college games, and the letter T calls it quickly wherever the player is, as long as a game is in play. Applies to every American football game, program and utility; nfl4 builds it first.
- The real rule (look it up again for each game's league and record it with the tag): a team timeout is granted only while the ball is dead; three per half; at most one per team in one dead-ball period (NFL 3-36-2 and 4-5-1, SRC-OFFICIAL; NCAA 3-3-4 and 3-3-4-a, the same, SRC-SECONDARY through an officials' association copy of the rule book). So a timeout may be called at every moment between the end of one play and the next snap or kick, including after the play is called and during the snap count.
- When T works: from the opening kick-off to the final whistle of a game being played, in every mode that has timeouts (nfl4: the N. F. L. rules), whoever has the ball. In every play menu (offense, defense, kicks, the two-point try), in every question asked during the game (the try choice, accept or decline, the challenge question, the onside question, a run-out question before the kick), during the huddle, the quarterback at the line and the snap count, and during the set-up of a punt, field goal, kick-off or try, up to the snap or the kick. One key, no Enter, no confirmation, no menu item to reach first; the menu item "Time Out" may stay as a second way.
- Quickly: T cuts the speech that is playing at once (the engine's own stop, 7.3, 7.3.1, 7.4.4: NVDA cancel, SAPI purge, JAWS flushed SayString), then the whistle sound and the timeout sentences; the clock stops at that moment (the time that would have run to the snap is saved).
- Before the snap: the called play is withdrawn and not run (no draws are made for it), both sides choose again and the play menu is spoken again from its top. The computer chooses its play again too (a new draw, only in the mode that has timeouts).
- While the ball is live (T pressed during a play's narration): the request is kept, the narration is not cut, and the timeout is granted the moment that play ends, before the next prompt, with the clock stopped there. One short word may confirm that the key was heard (nfl4 decides it in its design session) without cutting the play.
- Refusals keep the real limits: none left (" you have no time outs left. "), already one in this dead-ball period (" you have already called a time out. "), or no game in play. The refusal is one short sentence, said at once; then the game goes on exactly where it was (the snap count continues and the play runs, the question or menu is asked again). A refusal is never a foul.
- T is reserved: during a game no menu, question or list gives T to anything else (a menu that needs more letters than digits skips T), and only a box where the player types text (a name, a number) keeps t as a letter. Hot-key menus opened during a game (help, settings) close and call the timeout too. Between games (menus of the program, a franchise offseason) T does nothing new.
- The computer's own timeouts keep their rules; a computer timeout called before a kick that the player's team attempts (freezing the kicker) is a separate, recorded design choice.
- The original's exact mode keeps its keys unchanged when the original has no timeouts (the golden transcript proves it); the key help of 0.17 names T in the modes that have it; the debug log (7.11) writes `timeout_key` with the moment (menu, question, snap count, live play), whether it was granted or refused and why.
- Tests: T in every place listed above (each menu, each question, each step of the snap count and of each kick's set-up) calls the timeout with no other key; the play is not run and the menu comes again; T during a live play is granted at its end and never during it; the three limits refuse with their sentences and the game goes on; no in-game menu item has the letter T; T in a typed box is a letter; the original's mode is unchanged; the speech is cut within the engine's stop time (measure as 7.4.3 says).

### 7.17 The start-up choice and saved games (owner rule 2026-10-20, CLAUDE.md 0.23)
The owner, after hearing nfl4 load a saved game at start with no question: the player must choose whether to load a saved game, delete it or start a new game, and the program should have the other save and new-game features a player may want. Many old games (nfl4's football.sav, VB6 and DOS games alike) load a save as soon as the file exists and delete it when they read it; that loses the game on any crash after the load and gives the player no way out of a game they no longer want.
- What counts as saved: a saved game in progress, a season, a campaign, a league, a career, any file the program reads at start to resume where the player was. List them in S4.5 (CUSTOMIZABLE_CONTENT or a saves section of the spec) with where the original reads, writes and deletes each.
- The start-up menu: after the welcome (7.12) and before anything the original did with the save, when anything is saved. First a one-sentence summary of each save in plain words (nfl4: "You have a saved game: the Bears lead the Packers 14 to 10, third quarter, 6:12 left, saved on October 20 at 8:15 PM."), then a short menu read like the original's menus (Up, Down, digits, Enter; F1 repeats with its help sentence of 0.17; Esc as the original's Esc): 1 continue the saved game (the first item: Enter alone does what the original did), 2 start a new game and keep the saved one, 3 delete the saved game, 4 restore the save deleted last (only when a backup exists), then the program's own items (settings, help, quit). A season, campaign or league that is saved gets its own items in the same menu (continue the season, start a new season, delete the season), never a hidden second question.
- Delete safely: delete asks again ("Delete the saved game? Y. yes, N. no", starting at no); a deleted save is moved to a backup folder in the per-user folder (one level, the last delete), and "restore" brings it back; the log writes every save, load, delete and restore with the file and the reason.
- Keep the save until the game is over: loading never deletes the file; the save is removed (to the backup) only when the game it holds ends normally or the player deletes it or starts over with it. The original's delete-on-load is listed in the spec as a quirk that the game does not keep.

### 7.19 Radio-style banter replaces the original's comments, in sports games only (owner rule 2026-10-22, CLAUDE.md 0.27)

- Writing the lines: draft them in several independent batches (subagents work well: they return text, the session saves it at once and reads every line), split by topic so the batches do not repeat each other, and check the whole set with a script: the count, the length, plain ASCII, no digits, no brackets, no duplicate lines, no name of a real person or team from the game's own data, no word of a stop list (swear words, brands).
- Tests: in the game's own mode the pool holds the radio lines (count, IDs) and no original line; in the exact mode it holds the originals and the golden transcript is unchanged; the draw sizes are the same in both modes; F8 (comments off) silences it; a player's own line, `off` and a new number work; a player's file that still holds the original's lines in the game's own mode does not bring them back unless the player changed them (an entry equal to an original line is the default).

### 7.20 Four rules from a player's bug report (owner rule 2026-10-22, CLAUDE.md 0.28)
A player of nfl4 wrote four faults by e-mail; the owner: "make note of these for all future games I make, then fix all of these bugs in the current game." They apply to every game and are checked at S7.4 (menus, keys, speech set-up) and again before S9.1.

### 7.21 Real depth charts, real positions and playing time, in every sports game (owner rule 2026-10-24, CLAUDE.md 0.30)

The original author's games give every place of a group the same chance (Jim Kitchen's NFL football: the ball carrier one of six backs or six receivers by rnd(6), each tackler one of seventeen defenders by rnd(17)) and fill a short group with whoever is left. In the owner's own mode:
- Positions. Build the real names from the teams' own depth charts (0.19): a player's position is the group of the first chart row that names him (a safety the chart plays at cornerback is a cornerback; an edge rusher listed as outside linebacker is a linebacker), the roster page's position where the chart does not name him. A test lists every team's places with each player's real position and fails on a player at another position.
