### 7.4.4 The wait for the end of speech: no silence before the sounds (owner bug on Brain, 2026-10-13)
Owner: "after the prompt there is a long pause of silence, with NVDA, with SAPI 5 and with JAWS; it should not be there." The game says a prompt and waits until it is spoken (the original's blocking say), then starts the sounds. Any time between the last audible sound of the prompt and the engine's "done" is dead air. Measured on Brain's 28-character prompt, three different causes, one per engine; fix all of them in every game:
- SAPI 5: the voice's own trailing silence (0.66 s with FlexVoice2 Bill) is part of the rendered audio. Fix: trim it (7.4.1). Result: 662 ms to 20 ms.
- NVDA: the wait ran out the estimate (0.5 s + 0.09 s per character = 3.0 s for speech that took 1.0 s) because the end signal never came. NVDA has no finished call; the SSML mark callback of the controller header is an RPC callback that NVDA can deliver only while a BLOCKING speakSsml call is open, so with the asynchronous calls it never fires. What works (TESTED on NVDA 2026): `speakSsml(ssml, -1, 0, asynchronous=False)` returns exactly when NVDA has finished speaking (1.17 s for 1.0 s of speech), a `cancelSpeech` from another thread makes the blocked call return 1223 at once, and two blocked calls from two threads speak in order. So: one worker thread per backend makes the blocking calls one after the other (queue, generation counter), `wait_until_done` waits until nothing is in flight or queued, `stop` clears the queue and cancels, a call still open 2 s past the estimate is cancelled (hang guard), and texts without a letter or digit are sent as asynchronous SSML (a blocking call with nothing to say can hang for 301 s). Brain: speech/nvda.py. Result: 2,013 ms to about 160 ms (NVDA's own end of utterance).
- NVDA second trap (stale cancel): a `cancelSpeech` sent while nothing is speaking leaves NVDA with a cancel that kills the NEXT blocking call (it returns 1223 after a few milliseconds and says nothing), so every wait ended at once and the sounds started over the prompt. The game stops speech at start-up and on every key. So: send cancelSpeech only when a call of ours is open, queued or being held (also in close()), and make a call again once when it comes back 1223 within 250 ms although we cancelled nothing.
- JAWS: no end signal at all, so an estimate; it must be measured per engine (7.3.1: 0.08 s + 0.024 s per character; the first guess left 0.5 s of silence).
- How to find these: tool `game/tools/prompt_gap_check.py` (Brain): starts the built exe, chooses the first panning mode, records the speakers by loopback while the prompt is spoken aloud, and compares the moment the speech stopped being audible with the moment the log says the first sound was sent (`play slot` debug lines). Run it for every speech engine the game supports, in the built exe; the acceptance limit is 150 ms of silence. Give every backend a debug log line for each text it is given (`speak`) so the log shows the timeline.
- Never wait on an engine's reported end without checking it against what is audible: SAPI said "done" 0.66 s after the sound ended, NVDA's mark never came, and each looked fine in a unit test with a fake engine. A fake engine in tests must behave like the measured real one (the NVDA fake blocks until its speech time passes, returns 1223 on cancel, and has the stale-cancel behavior).

### 7.4.5 A voice that kills the program: build flag and crash guard (owner bug on Brain, 2026-10-13)
Owner: chose the SmoothTalker voice (the owner's own SAPI 5 wrapper of the 1990 Dr. Sbaitso engine, an x86 emulator that generates code at run time), and from then on the game did not start at all; NVDA loaded the same voice without trouble. Two separate fixes, both needed in every game:
- Root cause: the 64-bit exe made by PyInstaller carries the Control Flow Guard flag (IMAGE_DLLCHARACTERISTICS_GUARD_CF, 0x4000); python.exe does not. A CFG process kills itself with 0xC0000409 (fast fail) the moment a voice calls code it generated at run time. The 32-bit build had the flag too but survived. Source runs and the tests passed (they run under python.exe), so only a test of the BUILT exe finds it. Fix in the build script: clear the flag in the exe header after PyInstaller (Brain: `game/tools/clear_cfg_flag.py <brain.exe>`, two bytes, needs `pefile`; `--check` only reports), for both bitnesses. The smoke test checks the flag is off, and `game/tools/exe_voice_check.py <brain.exe> [seconds] [voice id]` starts the built exe with a given voice saved in its settings and reports alive or the exit code (3221226505 = 0xC0000409, 3221225477 = 0xC0000005).
- Crash guard, because any native voice can still kill the process, and a saved voice that crashes locks the player out for ever (the process dies before any menu). Brain: `data/voiceguard.py`, a file protocol: `voice_trial.txt` holds the voice id from the moment it is opened (start-up, or a pick in the F2 list) until it has spoken something to the end (SapiBackend `on_healthy`, one-shot) or the program closes normally; a trial file found at the next start means that voice crashed the program: it goes to `crashed_voices.txt`, the saved choice is kept in settings.txt but not opened, the first voice is used, and one spoken notice says so ("The voice SmoothTalker crashed Brain last time, so Brain uses ... for now. Choose it again in the voice list to try it again."). Choosing the voice again in F2 removes it from the list (another try, guarded again). Every call survives an unwritable folder. No-voice start and normal close clear the trial. Tests: unit tests of the file protocol, whole-program tests through app.main() with a leftover trial file, F2 pick arms the guard, the SAPI hook fires once.
- Test every exotic voice engine installed on the owner's PC (each TokenEnums family) in the BUILT exe in both bitnesses before release, with exe_voice_check; emulator, neural and 16-bit-era engines are the ones that break in a frozen process.

### 7.7 Customizable sounds (resolution chain)
Players can improve or replace any sound, especially wavs (better, longer, shorter, higher or lower quality), with no code change.
- Every sound has a stable ID (`menu_select`, `score_goal`) in `WAV_EVENT_MAP.md`; code uses only IDs.
- Resolution: the player's file for that ID; then the original wav (player's copy or shipped, per section 10); then the generated sound (7.8); then silence with a log entry. Never crash.
- Player sounds live in a sounds folder in per-user data, one file per ID named by ID. Wav always; ogg, flac, mp3 if the library supports them (verify). Plain-text `sounds.json` (created on first run, plain-word notes) maps ID to file, trims volume, sets looping, switches a sound off.
- Accept any rate, depth, channels, length; convert as needed; very long, empty, or corrupt files fall back to the next choice, are logged, with one short spoken warning.
- Logic never depends on sound length: if the original waits for a sound to end, wait for the end of whichever sound played (completion signal or measured length), never a fixed delay; timed pauses not tied to sounds stay timed. A sound switched off plays nothing and is not waited for (a player who wants a pause uses a silent file of that length; fixesforgames B-A17).
- Levels: the original's volume steps (DirectSound: hundredths of a decibel) are applied by the mixer, so a level that changes while a sound plays (crowd ramps, a volume menu) never restarts the sound; pan and the player's trim are baked into the samples (fixesforgames B-A15, nfl4 D-038).
- Accessible Sounds menu: open folder, reload without restart, export all generated sounds to wav, reset one or all, preview by name (list follows 7.4). Separate saved volumes: effects, music (if any), speech. Setting "Added sounds" (default on) switches generated gap-fillers on or off to hear only the original.
- README explains replacing a sound with an example. Android and iPhone reach the folder via the system file picker; IDs and chain are the same everywhere.

### 7.7.1 Numbered sound families the player can extend, and optional commercials (owner rule 2026-10-16, AGENTS.md 0.14)
Jim Kitchen's games name many sounds as a base plus a number (foot0.wav, foot1.wav, foot2.wav ...) and the code draws one of them: commentary, crowd remarks, hits, cheers. Every game lets the player add more of them, and optional commercials, by putting files in a folder. No code change, no settings file to edit.
- Finding families (S4.1). Group wavs whose names are base plus digits. A group is a POOL only when the code draws among its numbers for one event (a random pick, a rotation, an index chosen by the situation). Numbers that are different sounds for different events (nfl4's foot14 play noise, foot10 level line) are not a pool and get no added files: the code decides, never the name (B-P24). When one number range serves several events or several draw ranges, split it into pools named in plain words (`touchdown`, `interception`); the originals keep their file names as members, and the player's added files use the pool name as the base (`touchdown5.wav`). When every file of the game has the same base (nfl4: all 26 are `foot<N>`), the plain-word pool name is the only way to tell the pools apart. Each pool is one family entry in `WAV_EVENT_MAP.md`: family ID, first number (0 or 1), original members, event and call places, the original's draw rule (uniform, none twice in a row, none twice in a game, weighted, sequence), where the original gets its upper limit (a constant in the code, a probe of the folder, a count in a file), and any other pool that shares the draw. Member IDs stay `foot0`, `foot1` ... (stable, 7.7). S4.5 repeats the pools in `CUSTOMIZABLE_CONTENT.md` as customizable.
- Adding (S7.7). The player's sounds folder (7.7) is scanned for `<base><digits>.<ext>`: base case-insensitive, any extension the sound layer reads, any count of digits (leading zeros allowed), ordered by number. A file whose number is not an original member joins the family as a new member (`foot15.wav` after original `foot0` to `foot14`); a gap in the numbers is fine (never stop at the first missing number); a file with an original member's number replaces that member as in 7.7; `foot3 = off` in `sounds.json` or the Sounds menu takes a member out of the draw. Dropping files and choosing Reload (or restarting) is all the player does. The Sounds menu lists the pools by plain-word name with the original count and the added count, previews every member, tells the next free number, and, where the game has a general text prompt, a command "Add a sound to a pool": the player types or pastes the path of a file (a file picker is not reliable with a screen reader), and the program copies it in under the next free number. A game whose prompts are the original's fixed name prompts (nfl4: 30 characters) leaves the command out, records that in `DECISIONS.md`, and relies on the folder and the file name.
- Drawing. The original's draw rule applies unchanged to the grown family: the random range is the member count and a "none twice" memory covers the new members. With no added file the member list, the count and every random draw are exactly the original's, so conformance tests and golden transcripts run unchanged on the defaults. With added files the sequence differs from the original's, which is expected. A pool whose members are all off or unreadable is silent for its event (7.7 chain), never an error. An original member that is switched off leaves the draw (it no longer plays silence; say so where an earlier decision kept it in, nfl4 G-A3), but an original whose files are all unusable stays in, so a broken install does not move the draws. An added member has no level of its own in the original: give it the level, pan and pitch rule of the pool's most typical original and record that in `DECISIONS.md` (nfl4 D-068). Where the game has a banter file (7.9) the original numbered wavs are default lines made of one sound, added numbered files are more lines made of one sound, and all draw together by the original's rule.
- Bad files and size. A file that cannot be read is skipped, logged, and summarized by one short spoken message ("2 added sounds in touchdown could not be read"); the other members play. A very long file is handled as in 7.7. No fixed cap on added files; scan the folder listing, never probe numbers one by one, so ten thousand files do not slow the start (measure it).
- Commercials (optional, every game with breaks, even when the original has none). The spec's `CUSTOMIZABLE_CONTENT.md` lists the break points in plain words (sports: before the kickoff of the second half or halftime, end of a quarter, period or inning, between games, after the final; racing: between races; card, board, quiz and word games: between rounds or games; menu programs: none). Rules:
  - Nothing ships in it. The `commercials` folder is created empty beside `sounds` in per-user data with a plain-words note file; the README says the files are the player's own and the project provides none.
  - Files directly in `commercials` may play at any break; files in a subfolder named for a break (`commercials\halftime`) play only there. Any name, any format the sound layer reads, any count; names such as `commercial0.wav` work too. Text commercials: a game with a banter file (7.9) may also read a `commercials.txt` pool with the same markup, empty by default.
  - A Sounds menu setting, saved, default OFF even when files exist: off, every break, every second break, every third break.
  - It plays only at a listed break, after the game has spoken the break and before the next decision, never during play or while the game waits for a key. Speech is not cut: the commercial starts when the break's speech ends. A short spoken "Commercial. Any key skips it." comes first; any key stops it at once and that key is not passed on to the game. With the effects volume at zero or speech-only mode it is skipped without a wait. The spec states per break whether a game clock stands still (it does).
  - Order is a shuffle: none repeats until all have played. It uses its own random object, so the game's draws, seeds, saves and replays are identical with commercials on or off; nothing about a commercial is written into a save or a score.
  - An empty or missing folder with the setting on means no commercial, no pause and no message (once per session at most); a damaged file is skipped and logged (7.10); the folder and its note are recreated when missing.
- Tests: families (defaults draw exactly as the original; with k added files every member is reachable, only in-range draws occur, an off member is never drawn, a gap in the numbers works, a damaged added file is skipped, a replaced member replaces; a rescan after Reload; a folder of thousands of names scans within the budget); commercials (off by default; nothing played at a non-break; on and every Nth setting; a key skips and is swallowed; a missing, empty, corrupt or huge file is harmless; a golden transcript with commercials on equals the one with them off apart from the commercial events). Checklist A60 in `fixesforgames.md`; the loader and the slot go into the starter kit.
- README: one example each: adding `foot15.wav`, choosing a break folder, turning commercials on. Android and iPhone reach the folders through the system file picker; names and rules are the same everywhere.

### 7.8 Missing sounds: tone generator and music
Fill gaps with generated sounds and music in the spirit of DOS PC speaker sound, using best judgment; all replaceable (7.7).
Add when: (a) original PC speaker sounds are not gaps: reproduce exactly (ORIGINAL-TONE); (b) a referenced wav is missing or a slot has no file: fill it, note the original is missing; (c) silent events in a game that has sounds: leave silent unless a sound clearly helps a blind player understand what happened (confirm, error, turn change, score, win, loss, warning), decided case by case in `SOUND_DESIGN.md` (nfl4's `spec\SOUND_DESIGN.md` is the model, fixesforgames A36: a table of the silent events with a reason each; a game whose original already speaks every event keeps them silent, builds no tone generator work and skips S7.6); (d) a game with no sounds: a small tasteful set (menu move, select, back, error, confirm, start, end, win, lose, plus cues for its own events), short music only if it suits.
Limits: never change or remove an original sound; never change logic or timing for an added sound; never mask speech; keep additions short; mark GENERATED, list in spec game notes and README; the owner gets the full list in the listening rounds below, with a veto before release.
Choose by game type and event meaning, not one generic beep. Palettes: sports: whistle-like tone for play start/stop, buzzer for period or inning end, rising fanfare for a score, falling tone for turnover or out, noise burst with pitch drop for a hit, soft noise swell for a big play (never over speech), chime for new batter or possession. Racing: countdown beeps (three low, one high), engine tone rising and falling with speed via sweeps, tick or ding for checkpoint or lap, rough noise burst for collision, rising blip for gear change, pulsing warning. Adventure/role-playing: footstep ticks, noise-and-tone mix for doors and objects, chime for pickups, arpeggio for discovery, low slow pulse for danger, noise hits for combat, falling sweep for damage and rising for healing. Police/detective/action (e.g. cops98): alternating siren tone for alerts, radio-like beeps, sharp noise burst for a shot, rising two-note success. Card/board/dice/puzzle: tick for moving a piece, fast noise clicks for dice or shuffling, rising cue for a good move, low buzz for invalid. Quiz/word: rising right, low buzz wrong, ticking that speeds up for a timer. Menus/utilities: short blips for move, select, back, error, confirm. Frequent minor events: very short quiet sounds; rare important ones: longer, more distinct. Cues differ in pitch, rhythm, timbre; avoid harsh highs; keep energy mid-range so speech stays clear. Recommended character: retro DOS-era square and triangle waves at comfortable volume; ORIGINAL-TONE stays square-wave.
Built in, player's files first: ship default sound and music definitions inside the game so it has sound with no extra files. They are only defaults: as soon as the player puts a file for an ID in the sounds folder it is used, no setting needed; music too (a player's file replaces the tune; loops if `sounds.json` says so). A generated sound is never mixed with, or played before or after, the player's file for that ID.
Music only if it suits: short loops (~8-32 bars), simple melody, own volume and on/off, low default, lowered or paused during speech. Default decided automatically per game: on only if the original game had music, otherwise off (always off for text-heavy games); record it in `DECISIONS.md`; the player changes it in the Sounds menu.
Research first (start of S7.6): use web search and docs, not memory; write findings with sources in `SOUND_DESIGN.md`. Verify: the PC speaker is one square-wave voice from the timer chip (pitch from a divisor of a 1,193,182 Hz clock, gated by the speaker control port); QuickBASIC SOUND (Hz, duration in clock ticks), BEEP, PLAY (octave, tempo, length, notes, sharps/flats, rests, legato/staccato); synthesis (square, pulse, triangle, sine, sawtooth, noise; attack-decay-sustain-release envelopes; sweeps, arpeggios, noise bursts, vibrato; chiptune music: melody, bass, tempo, loops; pitch and stereo position for direction and distance); sound design for blind players (distinct, consistent, short, not tiring, room for speech); simple offline tooling (e.g. NumPy or plain Python sample buffers, standard-library wav writing). Record the tooling choice in `DECISIONS.md`.
Tone generator: module (e.g. `game/src/audio/tonegen`) building sounds from data files, not code: a sound = list of segments (waveform, pulse width, start/end frequency, duration, volume, envelope, vibrato, rests); melodies = notes and rests with tempo; music = tracks with loop points. Reads QuickBASIC SOUND values and PLAY strings directly so ORIGINAL-TONE entries are literal. Deterministic (seeded noise), fixed sample rate, mono or stereo, cached, played through the same audio layer, exportable to wav. Short attack and release everywhere to avoid clicks; balance levels against each other and speech.
Checking (the agent cannot hear): automatic code checks recorded in `SOUND_DESIGN.md` (length, peak below clipping, loudness vs other sounds, no click at start or end, no long edge silence, main pitch matches intent), plus owner listening rounds with the keyboard-only review tool `tools/sound_review` (the same tool used in 5.2; it exists since nfl4 P4 S4.1, README in `games\tools\sound_review`: for this review the round file's `labels:` are good, too long, too short, too high, too low, too harsh, too quiet, too loud, with `guess_text: good as it is` and `accept_all: yes`) that speaks each sound's name and event, plays it, and lets the owner repeat, go next, or mark: good, too long, too short, too high, too low, too harsh, too quiet, too loud, replace, or accept all remaining. 5-10 sounds per round; apply feedback, re-render, recheck; mark approved ones OWNER-CONFIRMED. Later the owner can drop a wav in the sounds folder or ask for a sound redesign session (read `SOUND_DESIGN.md`, change definitions, recheck, listening rounds).

### 7.9 Customizable names and game data
For games with customizable content (teams, players, race cars, drivers, tracks, characters, people, places, cities, street names, objects, items, creatures, ranks; most in sports, racing, adventure), keep names and data in plain text files outside the code so the player can optionally customize them.
- Inventory (S4.5) in `CUSTOMIZABLE_CONTENT.md`: list name, where it appears, entry count, each entry's ID and original name, original limits (count, min/max length, allowed characters, sort order, uniqueness, e.g. from fixed-length strings), per-entry attributes (ratings, speeds, stats, positions), where the original stores it (hard-coded, data file, save). Evidence tags apply; when unsure include it (the owner can veto later).
- Format: plain UTF-8 readable in Notepad and by a screen reader; line-based, minimal punctuation: one entry per line, clear field separator, `#` comment lines, plain-words note at top. Avoid formats where one missing comma or bracket breaks everything (strict JSON). Choose once in the first game, record in `DECISIONS.md`, reuse via `shared/`. Chosen in nfl4 (the first game with lists, D-032): one entry per line as `ID = name`, a `#` header with the format version on its first line (`# NFL Football 4 teams, format 1.`), permanent IDs (T01, D1, S0001), the name is what the voice speaks (a game whose original has no screen needs no second field; a `spoken=` setting after a semicolon is reserved), 1 to 30 characters without comma, semicolon or control characters, one `customize` folder for all player-edited files; the module `customlists` is written in S7.7 and added to the starter kit, nfl4 built it in S7.7 (D-048, fixesforgames A49): `data/customlists.py` holds the format and the healing of one list file and goes into the starter kit when the kit is refreshed. nfl4's `spec\CUSTOMIZABLE_CONTENT.md` is the model of the inventory (fixesforgames A36). One file per list (`teams.txt`, `cars.txt`, `streets.txt`). Entry = permanent ID (code, saves, sound mappings use it), display name, optional spoken-as text for names the speech engine mispronounces.
- Names and attributes are separate: by default only names are customizable; ratings, speeds, stats stay built in (original values) in a separate attributes table, so renaming never touches balance. Attribute editing is not enabled unless the owner asks for it; then it uses a separate file with the original values as defaults.
- Defaults ship inside the program and are never edited. The player's copies live in a customization folder in per-user data, same structure; a player's entry overrides the default with the same ID; missing entries use the default (updates add defaults without erasing customizations). A menu command creates commented copies to edit; another resets one list or all.
- Validate on load against original and logic limits (count, length, characters, duplicates, empty names). Bad lines are skipped or defaulted, never a crash; speak one short summary ("2 problems found in teams.txt, details are in the log"); log file, line, plain reason. A menu command checks files and reads results aloud.
- Do not hard-code a count the original logic did not; keep fixed counts (e.g. a set number of teams) unless the spec shows logic supports change; flexible counts only if the owner asks, then recorded.
- Saves and high scores store IDs plus a display-name copy, so renaming never corrupts them; if the original save stores names, read it correctly, map names to IDs. If the original kept lists in its own data files, the new format is primary, plus a one-time import of the original files. Renaming never changes sound IDs; an entry's own sound (e.g. a team theme) links by ID in `sounds.json`.
- Numbered sound files and commercials (owner rule 2026-10-16, AGENTS.md 0.14): the inventory also lists every pool of numbered wavs (foot0, foot1 ...) and every break point where a commercial may play; 7.7.1 says how the player extends them.
- Commentary and banter (owner rule 2026-10-14, AGENTS.md 0.12; every game with announcer remarks, jokes, taunts, cheers or random comments): customizable by the player with own TEXT and own SOUNDS. One file per pool in the `customize` folder (nfl4: `banter.txt`) plus a subfolder `customize\sounds\` for the player's sound files (any format the sound layer reads, 7.7). The original lines are the defaults with permanent IDs (nfl4: B001 to B142, built in from the spec's generated table, never typed); a player's line with an original ID replaces it, `ID = off` switches it off, new IDs add lines. A line is a sequence of pieces: spoken text and bracketed markup for what the code inserts (a drawn name, a team), the original's own sounds inside a line (nfl4's bleep), the player's sound files (`[sound file.wav]`), pauses, rate steps and alternatives; a line may be text only, sound only or both. The original's draw rule and call places apply to the whole pool (nfl4: equal chances, none twice in a game) and the original's off switch silences the player's lines too (nfl4: F8 comments). With the file absent or unchanged the game behaves exactly as the original (conformance tests run on the defaults). An owner question about crude or dated lines then only decides which lines ship switched off. S4.5 lists every such pool as customizable (never "built in") with its inserted pieces; S7.7 builds it on the shared `customlists` module; README: an example of a text line, a sound line and switching a line off. Model: nfl4 `spec\CUSTOMIZABLE_CONTENT.md` section 12, D-035. Built in nfl4 S7.7: the final markup words and limits are in `spec\CUSTOMIZABLE_CONTENT.md` section 14; the originals are written as the same markup, a line equal to the original's markup is the original, and one test per original line proves the original's order of speech, sound and key clears (fixesforgames A49, B-X30).
- Customize menu, keyboard and speech accessible: open folder, reload names, check files, reset to defaults. An in-game editor with the same validation only if the owner asks. README gives examples (rename a team, a car, a street). Same files on every platform.

### 7.10 Self-healing resource files: never crash, always know the originals
The game always knows its original names, choices, values. If the player deletes, empties, renames, or damages any resource file, the game detects it and recreates it from the original values; a missing or badly formatted file never crashes the game. The owner reports Jim Kitchen's games and other games for blind players did this: record exactly what each original did (files, contents, when) and match it; where the original did nothing, apply this anyway.
- Original values are built into the program as the source of truth (names, lists, attributes, setting defaults, sound and music definitions, the original's default high-score table if any). Player-reachable text files are editable copies and overlays: customization files (7.9), `sounds.json` and the sounds folder (7.7), settings, data tables, text or help files the original kept in its folder.
- Check at startup, on reload from Customize or Sounds menus, and whenever a file is read in play. Missing file: recreate from built-in values with the same header notes and format as the first-run copy. Missing folder: recreate it and its files.
- Partly damaged (some bad lines): keep the file, use originals for bad entries, report per 7.9.
