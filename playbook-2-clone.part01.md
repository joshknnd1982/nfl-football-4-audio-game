## 7. The game

### 7.1 Language (P6)
Decide after reverse engineering, before building; record in `DECISIONS.md` with the reason and tell the owner in one sentence (the owner may override later; say that changing gets costlier as the game grows). Default: Python with pygame-ce for audio and NO GUI toolkit. The window is a plain Win32 window made with ctypes (Brain's `ui/window.py`, about 150 lines: caption, key messages as virtual-key codes, Alt+F4, message box; tested by posting key messages to a hidden window; copy it to `shared/` when the second game starts). wxPython was 22 MB of the first 92 MB build for one empty window. Python suits simple turn-based games (easy to maintain, accessible); weaknesses are install size and wheels that lag the newest Python.

Language decision rule (owner, 2026-10-13, after Brain's size and latency review): STAY IN PYTHON unless a measured limit says otherwise; C# or C++ only as a last resort. Facts measured on Brain (P10), so later games need not rediscover them:
- Size: the original was 150 KB only because VB6 programs use runtimes already inside Windows; a Python build carries its own. First build 92 MB (64-bit) and 63 MB (32-bit), installer 44 MB. After the slimming recipe (8.1): 54 MB and 31 MB, installer 23 MB with both builds. After dropping numpy for `audioop-lts` (7.1.1, owner decision 2026-10-13): 25 MB and 21 MB, installer 13.3 MB; numpy would add about 28 MB (its OpenBLAS) to a 64-bit build and about 10 MB to a 32-bit one. Pure Python loops are too slow for resampling (a 10 KB sound at the lowest pitch is 120,000 output frames, about 100 ms per start), which is why the C code of `audioop` does that part.
- Speed: window in 0.18 s, first speech command at 0.55 s, sleep(1 ms) = 1.5 ms, mixer end reports within 5 ms, 42 sounds (67 KB) decode in 7 to 17 ms. Python was never the bottleneck of sound loading or key response; the waits were speech waits (7.4.3).
- Leave Python only when: (1) a hard real-time need that these numbers cannot meet, (2) the owner requires an install under about 15 MB with a measured shortfall after the slimming recipe and without numpy (7.1.1), or (3) a mobile target (Android, iPhone) where Python packaging is impractical: decide that at S12.1 with a small pilot, not now.
- Then choose C# on current .NET (self-contained, trimmed or NativeAOT: roughly 5 to 15 MB, strong COM and SAPI, Windows first) when Windows is the target; C++ or Rust with miniaudio (one small audio library for mixing, pitch and pan) only when cross-platform native audio and tiny size are both required. Any rewrite starts from the frozen spec and the Python game's conformance tables (port them to the new language's tests); the Python game stays the executable specification. Record the measurement that triggered the switch in `DECISIONS.md`. Do not ask about other platforms here: that is asked once in S11.4 (S12.1); meanwhile keep platform code behind interfaces (7.2), which costs little and keeps every platform open. Check `python --version`, `py -0p`, 32/64-bit; if Python is missing or unsuitable install the latest version with working wheels for every dependency (else the newest that has them, explain), user scope, yourself; same for any other language. A 32-bit build needs a 32-bit Python or toolchain beside the 64-bit one: install it too when a 32-bit build is planned.

### 7.1.1 Sound math: audioop-lts by default, numpy at the user's choice (owner decision on Brain, 2026-10-13)
Owner: "give the user the option to go back to numpy for a future game or program or utility which may require it", after trying Brain without it and being satisfied. Rule 0.11 in `AGENTS.md` is the short form.
- Why. numpy was 28 MB of Brain's 54 MB (64-bit) for a handful of jobs: resample for pitch, gain per channel for pan and volume, clip, decode a few wav formats, make a few tones. `audioop` does all of them in C. Python 3.13 removed it from the standard library; the package `audioop-lts` (PSF license, abi3 wheels for 64-bit and 32-bit Windows, about 30 KB, `audioop-lts==0.2.2`) is the same module, imported as `audioop`.
- Default code (starter kit): `Sampled` holds 16-bit PCM bytes, rate and channels (with `frames`, `seconds`, `peak`, `samples(channel)`). `render.py`: `audioop.ratecv(pcm + last frame twice, 2, channels, freq, 44100, None, 1, 0)` cut or padded to exactly the computed length (linear interpolation, the last sample held as the float version did); `audioop.tostereo(mono, 2, left_gain, right_gain)` for pan and volume of a mono sound (stereo sources: `tomono` per side, `tostereo`, `add`); output `pygame.mixer.Sound(buffer=bytes)` (no `pygame.sndarray`, which needs numpy). Decoding: 8-bit is unsigned (`lin2lin(bias(data, 1, 128), 1, 2)`), 24 and 32-bit `lin2lin(data, 3 or 4, 2)`, float by a short loop (not a number is silence, out of range is full scale), ogg, flac, mp3 and other codecs through `pygame.mixer.Sound(path).get_raw()` (mono doubled by the mixer is folded back to mono). `tonegen.py` is plain Python (`math`, `random.Random(seed)`).
- Measured on Brain: render every shipped wav at 12 pitches, 7 pans and 3 volumes with the numpy code (git tag `brain-1.0.2-numpy`) and with the new code and compare the bytes: 10,584 renders, identical lengths, worst difference 2 of 32,768 (inaudible); speed equal or better (388,521 output frames at the lowest pitch: 3 ms against 6 ms); plain-Python tone generation 2.6 to 3.4 million samples per second (numpy about 35 times faster); sizes in 7.1.
- Gotchas. `ratecv` ends one frame early: give it two copies of the last frame and cut to the computed length. Tests that need sample values use `Sampled.samples()`, `wavmaker.floats()`, `render.channel_peak()` and `audioop.max`, never arrays. Prove nothing imports numpy by running the whole suite with it blocked, from the `game` folder: `python -c "import sys; sys.modules['numpy']=None; import pytest; sys.exit(pytest.main(['-q']))"` (run from the game root, pytest reports 1 error in half a second). Add `--exclude-module numpy` to the build script; check `_internal` has no numpy folder and no OpenBLAS file.
- When the user may want numpy. The agent proposes it, with reason and cost, in S6.1 or whenever a need appears, and the user decides (rule 0.11; never silently): minutes of music or many generated sounds synthesized at every start (a minute of music is about a second of plain Python, so first try writing them once as wav files at build time or first run); filters, echo or reverb, equalizing, FFT or pitch detection, better than linear resampling; many voices mixed into one buffer in real time or effects that change while a sound plays; sample formats `audioop` has no call for.
- Output library. pygame-ce's mixer stays the output (owner decision 2026-10-13, after measuring): pygame and SDL are only about 5 MB of a 25 MB build, so OpenAL Soft (pan is a 3D law, no decoders, no tones), FMOD (proprietary, conditions on its free tier) and miniaudio (Python-callback mixing can glitch) would save at most 4 MB and none is a clean swap. wxPython is a window toolkit, not audio. Details and the revisit condition: fixesforgames.md B-A8.
- How. New game: `python tools/new_clone_from_kit.py <slug> <package> <game folder> --numpy-audio` lays the numpy versions of the audio code, its tests, requirements, notices, build script and tools (starter kit `alternatives/numpy-audio/`, with its own README) over the kit. Existing game: copy those files, install numpy in both environments, remove `--exclude-module numpy`, rebuild, run tests and smoke tests in both bitnesses. Record the choice and the reason in `DECISIONS.md`. When a kit file of either variant changes for another reason, change the other variant too and prove both (a throwaway game with and without `--numpy-audio`).

### 7.2 Requirements for every game
- 100% faithful to the spec (rules, wording, event order, sounds, timing, quirks) except required modernizations. Logic separate from UI and audio, testable without screen or sound card.
- Modern Windows, 32-bit and 64-bit; no DOS, DirectX 7, VB6 runtime, or Sound Blaster dependency.
- Size and speed budget (measured on Brain, 7.1, 7.4.3, 8.1): no GUI toolkit; build with the slimming recipe; report the installed size, the start time and the key-to-sound time in the P9 and P10 notes; any wait for speech before a sound is a latency and gets the "sounds start right away" setting (7.4.3).
- Audio: play original wavs (8-bit, low rates, mono); saved game sound volume control; match looping, overlap, cut-off; every sound replaceable (7.7); gaps filled with generated tones and music (7.8).
- Speech: every game, menu, utility speaks through SAPI5 in 32-bit and 64-bit builds; NVDA via the latest controller client DLL (7.3); optional JAWS through its COM interface when the owner chose it (7.3.1); output mode setting (automatic: NVDA if running, else JAWS if enabled and running, else SAPI5; NVDA only; JAWS only, if enabled; SAPI5 only); saved SAPI5 rate, pitch, volume controls; everything works by keyboard alone, nothing depends on sight.
- Title and welcome: the window title follows AGENTS.md 0.5.1 ("<Game name> by Josh Kennedy, inspired by <original author>"); the spoken startup words are the welcome of 0.16 ("Welcome to Josh Kennedy's <game name>, loosely inspired by <inspiration>.", 7.12).
- Debug log: every program writes the detailed debug log of AGENTS.md 0.15 from its first line, and can save a problem report for a player to send (7.11). Without it the agent cannot fix a bug that only happens on another player's PC.
- Names and data a player may change live in plain text files (7.9); settings per user (AppData), not beside the program; missing or corrupt files recreated from built-in originals, never a crash (7.10).
- Portability seams from the start: Windows-only code (registry, COM/SAPI5, NVDA DLL, JAWS COM, Windows paths) sits behind small interfaces (speech backend, storage paths, case-insensitive file lookup), as 9.3 describes, so Linux, Android, macOS, iPhone ports stay cheap.
- The process ends when the program is closed and never holds its own folder (7.2.1). Uninstall removes the whole program folder (8.2, 9.1.1).

### 7.2.1 The process really ends and never holds its folder (owner bug on Brain, 2026-10-13: "folder in use" until a restart, nothing in Task Manager)
Owner: after uninstalling, the leftover `My Brain` folder under Program Files could not be deleted ("folder in use") until the computer was restarted, and Task Manager showed nothing. Findings (measured, `game/tools/who_holds_folder.py` is the tool): a process whose CURRENT DIRECTORY is a folder locks that folder against rename and delete, and Windows' Restart Manager does not list it (only open files are listed), so nothing "uses" the folder anywhere the owner can look; the installer's "start now" box and shortcuts started the game with the program folder as working directory; the uninstall ran while the game was still alive (see 8.2); and a process can stay alive invisibly after its window is gone when a worker thread (speech engine COM, waveOut, a blocking engine call) does not return. Every game, from the starter kit (`src/<pkg>/data/lifecycle.py`, tests `tests/test_lifecycle.py`):
- At the start of `main()`, `leave_program_folder(program_dir, user_data_dir)` changes the working directory out of the program folder (to the per-user data folder, else the temp folder, else the drive root) whatever started the program. Any other code that needs a program file opens it by absolute path (`paths.program_dir()`), never relative to the working directory.
- Leaving: the window's close handler arms `arm_exit_deadline()` (a daemon `threading.Timer`, 6 s: logs "ending the process" and calls `os._exit`) so a close that hangs cannot leave the process behind; `main()` cancels it when it returns normally; the entry points (`__main__.py`, the exe entry file) end with `finish(main())`: flush and shut down logging, then `os._exit(code)`, which ends the process even when a non-daemon thread, a COM apartment or a native engine would keep it alive. The speech and audio objects are closed before that (so queued speech is stopped), and the crash guard (7.4.5) is cleared before the exit.
- No helper process, no autostart entry, no tray icon, no service: a game leaves nothing behind when it is closed (the exit deadline is a safety net, not the normal way out).
- Tests: unit tests of the three functions (a working directory in or below the program folder is moved, one outside or in a folder whose name only starts the same way is not, an unwritable data folder falls back to the temp folder, the deadline fires and can be cancelled, `finish` flushes the log and tolerates a non-number); an autouse fixture in `tests/conftest.py` restores the working directory after every test (a test that starts the whole program would otherwise move the next tests' directory); the built-exe smoke test (`exe_smoke.py`) starts the exe WITH ITS PROGRAM FOLDER AS WORKING DIRECTORY, presses Escape, requires the process to be gone within 2 s of its last log line ("Brain game closed") and the folder to be renameable afterwards. Measure the lingering time from the last log line, not from the key: Brain's original exit speaks its goodbye for about 7 s on purpose.
- Diagnose a report of "folder in use": `python game/tools/who_holds_folder.py "<folder>"` lists the processes holding any file of the folder and says whether the folder can be renamed; if nothing is listed and the rename fails, look for a process whose working directory is the folder (Process Explorer: Handles, type File, or Sysinternals `handle.exe`).

### 7.3 NVDA controller client
Owner-verified on Brain (2026-10-13, first game played with NVDA): the controller client DLL, NVDA-only output and automatic mode worked perfectly, and the owner liked that the voice and every other setting are saved and come back in the next session. Do the same in every game: ctypes against the x86 and x64 DLLs (the layout 7.3 says), a blocking speakSsml call on a worker thread to know when NVDA is done (NOT the SSML mark callback: it never fires with asynchronous calls; 7.4.4), SAPI5 as silent fallback, settings in one plain text file in AppData loaded and healed at start and saved at every change (7.10).
Get the latest from NV Access official sources (nvaccess/nvda repository, its controller client sources, official releases); confirm version and license live. 32-bit DLL in 32-bit builds, 64-bit in 64-bit (normally nvdaControllerClient32.dll / nvdaControllerClient64.dll; verify). Use speak, cancel, is-running check, optional braille; verify signatures in the downloaded header. Record DLL version and SHA-256 in `tools/` and README. DLL missing or failing, NVDA absent or closing mid-game: fall back to SAPI5 silently, never crash. JAWS support is optional and different (COM, nothing to bundle): 7.3.1.

### 7.3.1 Optional: JAWS (Freedom Scientific) support (owner request 2026-10-13)

Research (SJ.1) with WebSearch and WebFetch, Freedom Scientific official sources first (JAWS documentation and scripting pages on support.freedomscientific.com, the Freedom Scientific Developer Network (FSDN), What's New, system requirements, github.com/FreedomScientific), then secondary sources (open source libraries that call JAWS, forums), each fact tagged OFFICIAL, SECONDARY, TESTED (run on the owner's PC) or UNVERIFIED, with fetch date and links. Starting findings (fetched 2026-10-13; the guide overrides them):
- Interface (OFFICIAL, relayed: a 2012 Freedom Scientific support email quoted on a public JAWS scripting list; no current official page for FSAPI was found). FSAPI lets other programs control Freedom Scientific products, JAWS being the only supported one, and ships with JAWS 8.0 Update 2 and later. FSAPI.DLL holds a COM object (ProgID `FreedomSci.JawsApi`) and C exports declared in FSAPI.H; Freedom Scientific strongly recommends COM, because the caller need not find FSAPI.DLL on disk. The old file name jfwapi.dll appears in old posts (SECONDARY).
- Members (same source): `SayString(text, flush)` speaks, flush true discards speech in progress, returns true if JAWS is running and the text was scheduled, and returns before the speech finishes; `StopSpeech()` is documented to stop speech but DOES NOT on JAWS 2026 (TESTED, see "Verified on JAWS 2026" below: never use it); `RunScript(name)` and `RunFunction(name)` schedule a JAWS script or function by name (true means scheduled, not run; an unknown name makes JAWS speak an error). Any other members are UNVERIFIED: dump the type library on the owner's PC (tool of your choice, e.g. comtypes or pywin32 makepy) and record every member and signature.
- How other programs use it (SECONDARY: accessible_output2 as used by TWBlue, SRAL, many audio games): create the COM object; JAWS counts as running when a top-level window of class `JFWUI2` exists; speak with `SayString`, calling `StopSpeech` first when interrupting (this does not interrupt on JAWS 2026: use a flushed SayString, below); send braille with `RunFunction` and the call `BrailleString("text")`, replacing double quotes with single quotes because JAWS did not accept escaped ones; accessible_output2 puts one space before the text (reason undocumented: test whether it matters).
- Bitness: JAWS officially supports x64 on every operating system and ARM64 on Windows 11 (OFFICIAL, freedomscientific.com JAWS page); old guides mention a 32-bit JAWS. Whether today's install registers FSAPI for a 32-bit process is UNVERIFIED: read the class registration in both registry views (HKCR CLSID and WOW6432Node), note the DLL path and bitness, and test creating the object from a 32-bit and a 64-bit process.
- No speech-finished signal (TESTED: the type library has none): NVDA's blocking speakSsml call (7.4.4) has no JAWS equivalent; wait on an estimate (below).
- Voice: JAWS speaks with its own synthesizer, rate, pitch, volume, dictionaries and verbosity; the game's SAPI5 settings do not reach it (INFERRED: the members take no voice parameters).
- Nothing to bundle or redistribute: the JAWS installer registers the class, so a failure to create it means JAWS is absent or of the wrong bitness, not a bug. JAWS is proprietary paid software; the game only calls an interface of the player's own JAWS and copies no Freedom Scientific file. Whether Freedom Scientific's terms say anything about using FSAPI is UNVERIFIED: record what you find and claim nothing more in the README.
- Current JAWS release at fetch time: 2026.2609 (SECONDARY, Wikipedia, 30 September 2026); confirm by test that FSAPI works with the version installed, if any.
- Also record in the guide: whether JAWS is installed on the owner's PC (version, path), demo or trial limits that could make speech stop (look up, they would look like a bug), JAWS speech history or another way to capture what JAWS said (verify), and the JAWS key names for the owner's playtest checklist.

Verified on JAWS 2026 (Brain, 2026-10-13, TESTED on the owner's PC with a loopback capture; `tools/JAWS_GUIDE.md` has the numbers). These findings replace the guesses above and apply to every game; implement them in S7.1 and do not rediscover them:
- The interface is exactly six members, read with `pythoncom.LoadTypeLib(<FSAPI.dll path>)`: RunScript, SayString(text, flush), StopSpeech, Enable, Disable, RunFunction. Both a 64-bit and a 32-bit registration exist (HKCR CLSID and WOW6432Node), so a 32-bit build creates the object in-process: no helper process, nothing to bundle. With JAWS not running, SayString returns False with no error in under 1 ms. JAWS is running when a top-level window of class `JFWUI2` exists (TESTED).
- StopSpeech DOES NOTHING: speech goes on to its natural end (measured 1.9 s later). The cause of "the menus lag when I arrow quickly" in Brain was exactly this: stop then queue meant each new menu item waited for the old one to finish, up to 1.5 s late. The fix: stop = `SayString(" ", True)` (flush true, a space: cuts the speech in about 80 ms, says nothing); speaking stays `SayString(text, False)`. Sending that flushed space and then queuing the new text straight away is safe (TESTED: the new item is heard, about 90 ms after the command, same as when idle). Only send the flushed space when the game's own speech may still be playing (its estimated end plus a margin of 1.5 s), because the game calls stop on every key and JAWS's other speech is not the game's to cut. AMENDED 2026-10-23 (nfl4, the owner: "When I run the game with Jaws, speech is laggy when I press arrow and other keys. With NVDA speech is snappy"): (a) the FIRST text after stop() is said with `SayString(text, True)` (flush), the rest of that answer queued: it interrupts JAWS at once, whatever JAWS is saying then (its own echo of the key, a sentence that ran past the estimate); (b) a key waiting for the game ends a JAWS wait (the blocking say's estimate) once half the estimate has passed: JAWS gives no end of speech, the estimate is measured at the owner's rate, and at a faster rate every key waited for the rest of it; NVDA reports the real end, which is why it felt snappy. The game wires `speech.jaws.key_waiting = keys.key_waiting` where it makes its speech. fixesforgames B-S42.
- Wait for blocking speech by estimate: JAWS took 0.02 to 0.045 s per character on the owner's JAWS; use 0.08 s + 0.024 s per character (cap 30 s) (first guess 0.15 s + 0.035 s per character left a silent gap of 0.5 s before the sounds of every playback, so tune it against the measured length of the game's own blocking prompts, 7.4.3). Speech starts 0.05 to 0.1 s after the call.
- Make the check tools in the first JAWS game and run them with the owner's JAWS running (JAWS cannot be started by the agent, so ask the owner to start it, nothing else): `jaws_check.py` (availability, queue, flush, stop), `jaws_duration_check.py` (loopback: audible length per text, for the estimate) and `jaws_latency_check.py` (loopback: stop-then-speak start time against an idle start, for each way of interrupting). Method for loopback measurements: record the default speakers with the `soundcard` package (WASAPI loopback) in the main thread, issue the JAWS call from a `threading.Timer`, take the loud threshold from the idle level (0.0002; JAWS peaks near 1.0), join bursts closer than 30 ms; compare "idle" with "interrupting" starts. A test that asserts the stop is a flushed SayString (not StopSpeech) belongs in the unit tests, with a fake COM object.
- Run an arrowing latency test for every new speech engine, not only SAPI 5 (7.4.1) and NVDA: speak a long item, interrupt it 0.8 s later with the next item, and compare when the new item is heard with the idle start time. A difference over about 100 ms means the interrupt does not work.

Implementation rules (SJ.2, and S7.1 in new games):
- One backend class with the same interface as the NVDA backend (speak with interrupt, stop, is-running, finished-signal flag set to "not supported"), written once in `shared/`. COM on the speech thread with its own apartment (as 7.4.2 does for voices), late-bound object created lazily and cached, recreated once after a failure; use the COM layer the SAPI5 backend already uses.
- Running check: window class `JFWUI2` by FindWindow (ctypes) plus a created COM object, made at start and before every speak (cheap). Speak the text as is, queued (flush false); stop = a flushed `SayString(" ", True)`, never `StopSpeech` (below). No sentence splitting or memory-stream playback (7.4.1 is about SAPI5 only).
- Any COM error or false result: mark JAWS unavailable, speak that text through SAPI5 so nothing is lost, retry JAWS every few seconds and at the next menu. JAWS missing, closing or starting mid-game never crashes the game and never speaks twice.
- Output mode setting (same settings key as now, extended): automatic, NVDA only, JAWS only, SAPI5 only. Automatic = NVDA if running, else JAWS if running, else SAPI5 (keeps today's NVDA behavior; if both run, NVDA wins, and a JAWS player chooses "JAWS only"). Menu label stays short ("Speech output: automatic"). An unknown or old value heals to automatic (7.10). In JAWS mode the SAPI5 voice, rate, pitch and volume items still work and stay saved, but open with one short sentence: JAWS speaks with its own voice, change it in JAWS; game sound volume is unaffected.
- Waiting for speech to end: where the spec needs the game to wait (check spec sections 7 and 9), the JAWS backend cannot signal; use a conservative estimate from word count at a stated words-per-minute, record it in `DECISIONS.md` as an accepted default, confirm in the P8 playtest. Most turn-based games never wait.
- 32-bit builds: decide by the bitness test, record the reason. If a 32-bit process can create the object, use it in process. If not, either a small 64-bit helper program installed beside the game (started on demand, line-based UTF-8 commands speak, stop, quit over a pipe, never left running) or JAWS mode in the 64-bit build only, with the 32-bit build falling back to SAPI5 and saying so once; choose the simpler. The installer already installs the 64-bit build on 64-bit Windows (8.2), so most JAWS players run 64-bit anyway.
- Braille is not part of the first build. If the owner asks later: braille uses `RunFunction`, which runs JAWS script code, so strip double and single quotes, backslashes, parentheses and control characters, cap the length, and never pass player-editable text (customization files, 7.9) unsanitized.
- Documentation: Speech menu and F1 help text, README section on JAWS (what works, "tested with JAWS <version>" or "built but untested with real JAWS", the voice is JAWS's own), release notes, GitHub topic `jaws`.

Tests (SJ.3, and P8 in new games): with a fake JAWS COM object: text and flush reach SayString, stop reaches StopSpeech, not running falls back to SAPI5, a COM error mid-call falls back and later recovers, the output-mode table (NVDA only running, JAWS only running, both, neither, each forced mode), setting saved, parsed and healed, JAWS closing and starting mid-game, class not registered or COM layer missing, thousands of speak calls, the sanitizer if braille exists. Real JAWS, if the owner has it installed: scripted check that the object is created and `SayString` returns true, `StopSpeech` works; capture the speakers by WASAPI loopback (7.4.1) and compare start and stop latency with NVDA on the same text; then a short owner playtest, keyboard-only: game starts and speaks the title, menus speak, arrow keys interrupt old speech, the voice items say JAWS speaks with its own voice, closing JAWS mid-game switches to SAPI5, NVDA mode still works. No JAWS available: label the feature "built and tested with a fake JAWS only" in README, release notes and `PROJECT_STATE.md`, ask the owner once whether they or a JAWS user can test (a license is theirs to supply, 0.8), never claim it works with JAWS; when tested, record JAWS and Windows versions and replace the label.

### 7.4 SAPI5 engine list (stable with thousands of entries)
(Superseded in part by 7.4.1 and 7.4.2, which are owner-verified: use SAPI's own enumeration and the engine-then-voice choice described there.) List all SAPI5 engines; stay stable and responsive with 1000+. Enumerate tokens from the registry (native and WOW6432Node views, registry view flags so 32- and 64-bit tokens both appear), not by creating a COM voice per entry; read display names cheaply; create a COM voice only for the chosen one. Per-entry error handling so one broken token never stops the list. Fill the list in one operation or use a virtual list, never thousands of single adds with redraws. Offer type-ahead or search. Slow enumeration off the main thread, COM initialized per thread. Cache; refresh on request. Mark bitness (a 32-bit process uses only 32-bit engines, a 64-bit one only 64-bit): either separate builds showing compatible voices, or a small 32-bit helper process beside a 64-bit game; choose the simplest, record it. SAPI5 rate -10..10, volume 0..100; no pitch property, so apply pitch through XML markup in the text (not every engine honors it: test, document). Test with thousands of fake tokens plus real and deliberately broken ones.

### 7.4.1 SAPI5 speech latency and playback (owner-verified on Brain, 2026-10-13: "the lag is resolved")
Do this in every game that speaks through SAPI5; it was found by measuring on the owner's PC (1,789 voices, 19 voice families, many old third-party engines).
- Why: SAPI's own audio output makes "stop speech" (purge) block for hundreds of ms on some voices (Brain: FlexVoice2 Bill 350 to 710 ms), so every arrow key waited for the old speech. Direct SAPI also stops 100 ms later than a player you control.
- Method: on the speech thread render each text into an SpMemoryStream (SpAudioFormat type 34 = 44.1 kHz 16-bit mono; the voice's volume, rate, pitch and choice stay SAPI's), read the bytes ONLY after WaitUntilDone says the engine is finished, and play them through winmm waveOut with ctypes (Brain: speech/waveout.py; stop = waveOutReset, 3 ms; a watchdog drops a device that never reports a block done). Texts over about 60 characters are made and played sentence by sentence so they start early.
- Never read the memory stream while the engine is still writing it: the data changes afterwards and words are skipped (Brain's first streaming build did this; the owner heard it). Do not play speech through the game's own mixer (measured: no gain over waveOut) and do not build a custom ISpAudio COM object like NVDA's (not needed).
- Speed probe per voice, at start and after every voice change: make a short text into memory; if it is not done within 0.25 s the engine makes speech no faster than it speaks it (Orpheus Classic, Prose 2000, neural voices): speak that voice directly through SAPI instead (and point it back at the default output).
- Silent text: if a voice returns 0 bytes for a text, try other ways to write it: a comma between numbers that only a space separates, letters folded to plain ASCII (c-cedilla, curly quote), digits spelled out. BestSpeech Fred makes no audio for "Infovox230 1.12 ..." or for non-ASCII letters; before this fix 113 of 1,789 voice names were silent in the voice list. Test by rendering every voice name once. Also render every KIND of sentence the game says (a pytest plugin records them, a signature reduces them to a few hundred) with one voice of every installed engine, in both bitnesses, with the program's own pieces and repair (nfl4 S8.3: `game/tools/sapi_render_check.py`); old emulated engines die on a token of only stops (SAM) or a word of thousands of letters (Votrax), so the pieces handed to a voice never hold either (fixesforgames B-S28).
- Keep spoken menu labels short (they are said at every arrow key); put hints in the F1 help.
- Verify without ears: capture the speakers by WASAPI loopback (Python package soundcard in a separate tools environment) and compare the game with the screen reader speaking the same voice; also read the owner's screen reader settings (NVDA: %APPDATA%\nvda\nvda.ini: Brain's owner ran Fred at rate 90 = SAPI +8 through the BestSpeech add-on, while the game used the voice's own rate 0: the last difference they heard). Survey one voice per installed voice family with a latency tool, not only the first voice. Brain's tools: game/tools/key_latency_check.py, speech_latency_check.py, audible_latency_check.py, interrupt_latency_check.py, audible_keys_check.py.
- Result on Brain (loopback, same PC): start 58 ms and stop 49 ms, NVDA 73 and 73; key read to speech handed over 6 to 20 ms.
- Cut the silence at both ends of every rendered text before playing it (Brain: `trim_silence` in speech/waveout.py, keep 15 ms before and 60 ms after, audio that is silent from end to end stays as it is, odd byte counts are left alone). Some voices end every utterance with half a second of digital silence (FlexVoice2 Bill: 0.66 s after a 1.9 s prompt), and a game that waits for "the speech is done" then waits that silence out before it does anything (7.4.4).

### 7.4.2 Choosing a SAPI5 voice: engines, all voices, letter keys (owner-verified on Brain, 2026-10-13: "all is good")
Build the voice choice like this in every game (Brain: game/functions.py choose_voice, speech/voices.py, game/spoken_menu.py ListPicker):
- Take the list from SAPI's own enumeration (SpVoice.GetVoices), not the registry: on the owner's PC SAPI lists 1,789 voices and the registry 249 (7.4's registry route misses most). Read id and description only (0.5 s for all), on a background thread with its own COM apartment, cached; never create a COM voice per entry.
- Engine of each voice, from the token only: the name of its TokenEnums registry key for enumerator voices (Bestspeech, OpenEVV, DoubleTalk...), else the token's Vendor attribute, else "Other voices". Brain's PC: 27 engines.
- Step 1 an engine list: first item "All voices of all engines, N voices", then each engine alphabetically with its voice count; it opens on the engine of the voice in use. Step 2 the voices of the chosen engine (or all voices), opening on the current voice marked "current voice". Escape in a voice list goes back to the engine list on the same engine; Escape in the engine list leaves the choice. Enter chooses, says the voice set and a sample, saves it. The engine's first voice is stored as "no saved voice" (the original's choice).
- Navigation in every list: Up, Down, Page Up and Down by ten, Home, End, and an F1 help that describes the letter mode in use. Letter keys are a saved setting in the speech menu ("Letter keys in lists", settings file key list_letters = type | first): type = type-ahead search with a one second pause (default, the first match from the top, then names that contain it), first = a letter jumps to the next name that starts with it, the same letter again goes on to the next, wrapping (names are matched on their first letter or digit). Enter on the setting restores the original. Both modes apply to the engine list and the voice lists.
- Keep every spoken list item short (said at every arrow key); the engine item is "<engine>, <n> voices".
- Test every voice name once with the owner's voice (render to memory, see 7.4.1): names the voice cannot say must be retried written another way, or the list has silent entries.
- Tests to copy: engine grouping and order, the engine path of fake tokens, Escape levels, all-voices count, type mode and first-letter mode (wrap, repeat, no match), the setting saved and parsed, stress test with thousands of voices through the new path (a new menu level changes every test that scripts the old path: keep one helper per path).

### 7.4.3 Responsiveness: key to sound, start time, sound loading (Brain P10, 2026-10-13)
Owner reports "not very responsive when loading sounds". Measure before changing anything; Brain's measurements (loopback capture of the speakers, tools in `game/tools/`) found:
- Loading sounds is not slow. 42 original wavs total 67 KB; first decode of all of them 7 to 17 ms, rescan at every playback start 2 to 8 ms, cached picks 0.04 ms each, the built program's cold start (window at 0.18 s, first speech command at 0.55 s; a very first run after an install can take 3 s while Windows scans the new files). Do not build preloading or threads for this.
- The wait the owner hears between Enter and the first sound is the spoken prompt the original waited for (" Press the space bar to stop.", a blocking say): 2.6 s with a slow SAPI voice (median 2,667 ms Enter to first sound; the game itself adds only about 70 ms after the prompt ends, most of it the sound device), 0.65 s with a fast JAWS voice. The original behaved the same, so the default stays, but every game gets a setting.
- Setting (F3 sounds menu, last item, saved as `sound_start` in settings.txt): "Sounds start: after the spoken prompt, original" or "right away, while the prompt is spoken". Right away means the prompt is queued (say_async) instead of awaited (say); measured Enter to first sound 62 ms against 2,667 ms. Rule for every game: find each blocking say that precedes a sound or action the player is waiting for, keep it by default (fidelity), and offer the one switch; tests: the default waits, the setting does not, Enter restores the original, "restore original sound settings" resets it, settings file round trip.
- Engines that cannot report the end of speech (JAWS) wait on an estimate; a wrong estimate is the same latency (7.3.1: 0.5 s too long at first). Measure the engine's real speaking time per character with the loopback tool and fit the estimate; SAPI 5 (render in memory, trim the silence, play through waveOut, 7.4.1) knows its exact end, NVDA's blocking call returns at the end of speech (7.4.4).
- Tools to copy: `playback_start_latency.py` (built exe: Enter to first sound, split into key to speech command, prompt, game overhead; accepts extra settings lines to compare modes), `startup_time_check.py` (process start to window, first log line, first speech command), `sound_load_timing.py` (library construction, first decode, rescan, cached picks), `jaws_latency_check.py`, `jaws_duration_check.py`. Method: record the default speakers with the `soundcard` package (WASAPI loopback) in the main thread, trigger from a timer or posted key, take the loudness threshold from the idle level, compare against an idle baseline; a PC with other sounds playing gives garbage, so wait for a quiet second first.
- Before and after, put the numbers in `DECISIONS.md` and the P9 notes.
